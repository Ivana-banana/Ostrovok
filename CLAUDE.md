# CLAUDE.md — правила проекта

Режим: финал

Пиши на ~80% ASD-STE100: короткие предложения, одно действие — одно предложение,
один термин — одно значение. Так же пиши отчёты и описания PR.

Строку «Режим:» читают хуки, `scripts/finish.sh` и агенты. Значения: `сборка` или
`финал`. Меняет только человек, одним коммитом на вехе заморозки (раздел «Режимы»).

## Задача

<!-- kickoff:task -->
**О!дин запрос — AI-агент путешествий.** Агент превращает одно сообщение путешественника («тёплое море в ноябре, недорого, с ребёнком») в готовый сценарий поездки и ведёт по этапам: уточнение, вдохновение и выбор направления, подбор и сравнение, объяснение выбора, сборка плана и корзины со стыковками, имитированная покупка, пересборка плана при новых условиях. Успех — на защите жюри даёт незнакомые запросы, и агент доводит каждый до оформленной (имитированной) покупки, объясняя выбор и пересобирая план без поиска с нуля.

- Ещё две user story условия: Островок — путь до покупки внутри сервиса и поездка целиком; отель — рекомендовать тем гостям, которым он подходит, чтобы было меньше отмен.

- Пользователь: путешественник, который сейчас планирует поездку в 4–10 вкладках и сам сверяет даты, стыковки и трансферы.
- Условия — `task/` (копия страницы хакатона). Исследование — `research/`,
  справка по предметной области — `research/domain.md`.
- Сроки и оценка — `task/hackathon-rules.md` (rules.pdf). Сдача — до 2026-10-29 10:00 МСК.
  Этап 1: жюри без нас оценивает репозиторий, README, видео и запуск, отбирает до 10 финалистов.
  Этап 2: питчинг 2026-10-30 17:00, онлайн, 5 мин доклад + 5 мин вопросы. Вехи — `docs/timeline.md`.
- Неизвестный факт пиши как `[СПРОСИТЬ]` и строкой в `docs/questions-for-organizers.md`.

<!-- kickoff:criteria -->
Приоритеты жюри — со слов организаторов, Q&A №1, 2026-10-27. Веса не названы. Порядок важности:

1. Переиспользуемость решения реальным бизнесом.
2. Архитектура.
3. UI/UX.
4. Удобная проверка и запуск. Это наша ответственность: сайт или `docker compose` — выбираем сами. Видео: 2–3 минуты достаточно, предел — 10.

Допущения команды: переиспользуемость — источники данных и LLM стоят за адаптерами, замена провайдера не трогает ядро. Без доведения незнакомого запроса до имитированной покупки пункты 1–4 не оцениваются. Ключи и внешние модели — организаторы ответят отдельно (`docs/questions-for-organizers.md`).

### Ловушки данных

<!-- kickoff:traps -->
- `TRAP-1` У жюри нет ключа LLM API — запуск `docker compose up` по правилам: без ключа агент должен деградировать честно (правила/шаблоны), а не падать; спросить организаторов
- `TRAP-2` Неизвестные запросы жюри — защита: каталог должен покрывать любое направление, а не 5 заготовленных городов
- `TRAP-3` Варианты написания топонимов — геокодинг: нормализация названий и fallback-поиск до вызова гео-API
- `TRAP-4` Выдуманные цены и рейсы LLM — любой LLM-шаг, который сам пишет цены: цены, время и стыковки — только из инструментов; LLM их не генерирует; проверка ссылок на id
- `TRAP-5` Стыковки по времени и часовым поясам — прилёт → трансфер → заселение: детерминированная проверка таймлайна с часовыми поясами
- `TRAP-6` Нестабильная сеть и публичные демо-API — OSRM demo, Overpass, GitHub: кэш и снапшот данных в репозитории, работа без сети на демо
- `TRAP-7` Моковые данные выдаются за реальные — демо: пометка «синтетика» в UI у каждой цены
- Тривиальный ответ: Один промпт к LLM «спланируй поездку» → текст маршрута в чате: нет корзины, нет проверки стыковок, нет пересборки, цены выдуманы. По условиям это «пересказ выдачи в чате — не решение». Покрытие 6 этапов пути — 1–2 из 6 (вдохновение и текст плана). Это планка: `make eval` печатает её (`eval/baseline.json`).
- Тест на каждую ловушку содержит её id (`TRAP-1`…); `make check` это проверяет.

## Как работаем

1. Возьми задачу: `bash scripts/issues.sh free`, затем `take <N>`. Нет подходящей —
   `create`, затем `take`. Без взятой задачи файлы не меняем и не коммитим: это
   проверяют хук `check-issue.sh` и `.githooks/`.
2. Работай в worktree:
   `git worktree add .claude/worktrees/<N>-<тема> -b worktree-<N>-<тема> origin/main`.
3. Закоммить свои пути (`git add <пути>`) и влей: `bash scripts/finish.sh` из worktree.
   Скрипт делает merge `origin/main`, проверки по режиму, PR, merge, уборку (`GIT.md`).

- Занятая `area:` не держит: `take` предупреждает. Договорись с соседом в задаче
  (`issues.sh note`), чтобы не править одни файлы.
- Чужая задача без движения дольше `TAKEOVER_MIN` минут (`.env`) — `take`
  перехватывает её с комментарием. Перехват — продолжение чужой ветки.
- Человек сказал «возьми #N» — `take <N> --human`. Это выполняется всегда.
- Риск показа или сдачи — сразу задача с меткой `blocker`. `main` всегда зелёный.
- Запрещены force-push, `rebase`, `--amend`, `git add -A`, push в `main`, трейлеры
  соавторства ИИ.
- Цели `make` — единственный интерфейс: `setup`, `lint`, `check`, `demo`, `eval`,
  `eval-final`, `e2e`. Команд стека в обход `make` в отчётах не пишем.

## Режимы

| | сборка (по умолчанию) | финал |
|---|---|---|
| Тесты | агент гоняет тесты своих файлов и `make lint`; полный `make check` — один раз в `finish.sh`, PR с красными он не создаёт | только человек по просьбе «полный прогон»; `finish.sh` — только `make lint` |
| `reviewer` | каждый PR | метка `contract`, формат данных, diff > 300 строк |
| `docs/decisions.md` | ведётся, строка ≤ 200 символов | только решения о модели, формате, контракте |
| Новые md | отчётов и планов в md нет — отчёт в чат | запрещены хуком, кроме README |
| `eval-final` | закрыт | один раз на замороженный коммит (`evaluator`) |

Переход в «финал»: веха заморозки из `docs/timeline.md` → cut line из BUILD-PLAN →
человек меняет строку «Режим:» одним коммитом → `jury` на этом коммите.

## Автономия

- Агент подтверждает свои решения сам, через свежего субагента: `reviewer` для кода,
  скептик (любой свежий субагент с задачей "find why this decision is wrong") для решения.
- Два отклонения подряд — арбитр `jury`. Его вердикт окончательный для агента.
- Человек подтверждает только:
  - заморозку контрактов;
  - план задач (до создания Issues);
  - изменение формулы или методологии, которая идёт на слайд;
  - внешние действия: массовый парсинг, регистрации, платные API, письма организаторам;
  - переключение режима.
- Блоки «ЗАДАЧА / СДЕЛАНО» печатай в чат. Они не ждут ответа.

## Проверка

- Перед PR: `git fetch --prune && git merge origin/main`, затем проверки по режиму.
- Ошибка в доменной логике — сначала воспроизводящий тест.
- Каждой ловушке данных — тест. Тесты не удаляем и не отключаем.
- Holdout (`eval/holdout.tar.gz`) не читаем никаким инструментом. Его открывает
  только `make eval-final` на заморозке. Работаем по `eval/cases*` и `make eval`.
- «Работает» пишем только с командой и её выводом. Числа для питча — только из
  вывода `make eval`, `make eval-final` и замеров с командой.

## Документы

- Отчёт — в чат: что изменилось для пользователя и чем проверено. Diff не пересказываем.
- Описание PR — `Closes #<N>` и суть правки.
- Документ правим только в своём случае:

  | Файл | Когда правим |
  |---|---|
  | `README.md` | изменились команда, адрес, ограничение, замер или функция для жюри |
  | `docs/decisions.md` | решение о модели, формате, контракте, правилах (D-NNN) |
  | `docs/timeline.md` | сдвинулась веха или cut line |
  | `docs/questions-for-organizers.md` | вопрос или ответ организаторов |
  | `research/` | факт предметной области с источником |
  | `pitch/QA.md` | вопрос жюри и честный ответ с цифрой |

- Строка `docs/decisions.md` — что выбрали, до 200 символов. Почему — в коммите.
- Правка заменяет устаревший текст, а не дописывает новый.

## Код

<!-- kickoff:stack -->
Архитектура — `docs/adr/ADR-0001-avtomat-etapov-dag-optimizator.md`: Автомат этапов + TripSpec + DAG пересборки + детерминированный оптимизатор (C6).
Типизированная спецификация поездки `TripSpec` — единый источник правды. LLM (OpenAI-совместимое API) делает только две вещи: извлекает/правит `TripSpec` из текста и пишет объяснения по фактам инструментов. Подбор, сравнение и проверку стыковок делает код: оптимизатор (направления × отели × транспорт × трансферы) и чекер таймлайна. Узлы плана связаны DAG-ом: правка спеки пересчитывает только зависимые узлы.
Пресет: `web-fullstack` (`make setup PRESET=web-fullstack`; признаки в ADR: fastapi, react, vite, web).
Контракт — `backend/src/api/contracts.py` и зеркало `web/src/contracts.ts`; потребители — в docstring контракта.
<!-- /kickoff:stack -->

- Плоский код, без абстракций «на будущее». Правь только зону задачи.
- Модули связаны только через контракты. Контракт меняется отдельным PR с меткой
  `contract` и списком потребителей.
- Секреты — только в `.env`. Данные — вне git (`data/`): сырые данные коллектора — в GitHub Releases, агрегаты без названий — в git (`backend/src/api/`); примеры — `tests/fixtures/`.
- Идентификаторы и комментарии — английские. Интерфейс и документы — русские.
- Промпт субагенту (`Agent`, `Workflow`, `SendMessage`) — на английском. Отчёт человеку — на русском.

## Агенты

Роли — `docs/agents.md`, определения — `.claude/agents/`. Личный протокол участника —
скилл `/orchestrate`: свои задачи → worktree → `builder` → `reviewer` → `finish.sh`.
Общего оркестратора нет. Перед демо — `silent-failure-hunter` (тихие ошибки).

Модель по умолчанию — `.claude/settings.json` (`model`, `effortLevel`). Разовый прогон
`make check` с кратким итогом — скилл `/tests`. В конце хода тесты не запускаются.

Часть участников работает в Codex. Его правила — `AGENTS.md`: те же задачи, роли и хуки.
Слой Codex (`.codex/agents/`, `.agents/skills/`) генерирует `python3 scripts/codex-sync.py`
из `.claude/agents/` и `.claude/skills/`. Правишь роль или скилл — запусти его и закоммить
результат в том же PR.

## Известное — тревогу не поднимаем

- `team.py` планировщика делает rebase и push, но только в своей ветке `arch/<run>` и
  из Python. Это не нарушение запрета rebase. Хуки ветку `arch/*` не проверяют.
- Очередь `team.py` живёт только на этапе проектирования. На сборке задачи — только в
  GitHub Issues. Две очереди одновременно не ведём.
- Grill планировщика — вопросы по условиям задачи. `grill-me` — только для решений
  о процессе.
- `.arch/`, `_arch/` и scratchpad агента — в белом списке `check-issue.sh`.
