# architecture-planner

Скилл для Claude, который превращает папку с условиями задачи (например, хакатона) в несколько принципиально разных, проверенных архитектур. Из них можно осознанно выбрать одну, после чего скилл фиксирует решение в ADR и пишет план сборки.

Скилл не просто «придумывает архитектуру». Он:

- уточняет условия задачи, но не навязывает решение;
- пишет тестовые сценарии, на которых сравниваются все варианты, и откладывает часть сценариев для честной проверки;
- генерирует до 15 вариантов в две волны: первая — до поиска готовых решений, вторая — после него, чтобы найденное не «притянуло» все идеи;
- ищет похожие проекты, open source и готовые API;
- оценивает варианты анонимной панелью критиков по абсолютной шкале, а всю арифметику считает скриптом;
- проверяет, насколько рейтинг устойчив к весам критериев;
- исследует открытые вопросы в порядке их полезности для решения;
- прототипирует лидера против простейшего варианта;
- показывает весь процесс в дашборде и списке задач.

Работает в одиночку, командой из N человек в одном репозитории и в режиме автопилота, когда вас нет рядом.

## Установка

**claude.ai / приложение Claude.** Загрузите файл `architecture-planner.skill` в чат и нажмите **Save skill** на карточке файла, либо добавьте его в разделе скиллов в настройках.

**Claude Code.** Распакуйте архив в папку скиллов:

```bash
# для всех ваших проектов
mkdir -p ~/.claude/skills && cd ~/.claude/skills
python3 -m zipfile -e /path/to/architecture-planner.skill .

# или только для одного проекта (удобно для команды: скилл попадёт в репозиторий)
mkdir -p .claude/skills && cd .claude/skills
python3 -m zipfile -e /path/to/architecture-planner.skill .
```

После этого появится команда `/architecture-planner`.

**Требования.**
- Python 3.8+ (только стандартная библиотека, ничего ставить не нужно).
- `git` — только для командного режима.
- Веб-поиск — желателен для этапов поиска готовых решений и ресерча. Без него скилл работает, но помечает оценки как опирающиеся на общие знания.
- Субагенты (инструмент Agent/Task в Claude Code) — желательны. С ними критики и отложенные сценарии по-настоящему изолированы. Без них скилл работает, но независимость слабее, и отчёт честно это указывает.

## Быстрый старт

1. Сложите в одну папку всё, что известно о задаче: условия, критерии жюри, примеры данных, свои заметки и ресерчи. Формат любой: md, txt, pdf, docx, xlsx, код.
2. Запустите:

   ```
   /architecture-planner --input ./hackathon
   ```

   В claude.ai загрузите файлы и напишите обычным текстом: «спроектируй архитектуру по этим файлам».
3. Ответьте на вопросы об условиях задачи (раунды grill-me). У каждого вопроса есть рекомендованный ответ: можно просто согласиться.
4. Подтвердите бриф, просмотрите отсев кандидатов, одобрите прототипы.
5. Получите `ARCHITECTURE-REPORT.md`, выберите вариант — скилл напишет ADR и план сборки.

Типичная длительность: экспресс-режим — около часа, полный — несколько часов, в зависимости от ресерча и прототипов.

## Флаги запуска

| Флаг | Что значит | По умолчанию |
|---|---|---|
| `--input <папка>` | Папка с условиями задачи и материалами | спросит |
| `--express yes\|no` | Быстрый режим | `no` |
| `--team <N>` | Сколько человек прогоняют план параллельно | `1` |
| `--autopilot yes\|no` | Работать без вас, принимая рекомендованные решения | `no` |
| `--budget <USD>` | Сколько можно потратить на API в прототипах (для автопилота) | нет |
| `--run <id> --member <имя>` | Присоединиться к командному прогону | — |

Флаги можно писать и словами: «экспресс, нас трое», «я ухожу, решай сам».

Примеры:

```
/architecture-planner --input ./hackathon --express yes
/architecture-planner --input ./hackathon --team 3
/architecture-planner --input ./hackathon --autopilot yes --budget 5
/architecture-planner --run hackathon-1005 --member boris
```

## Режимы

| | Полный | Экспресс |
|---|---|---|
| Когда | Есть дни, решение дорого переделывать | Дедлайн через часы |
| Сценарии | 10–20, из них 3–5 отложенных | 6–8, из них 1–2 отложенных |
| Кандидаты | 8–15 (останавливается, когда идеи начинают повторяться) | 5–8 |
| Финалисты → итог | около половины → до 5 | около половины → до 3 |
| Ресерч | пока ответы могут сменить лидера | то же, максимум 4 вопроса |
| Критики | панель из трёх ролей | один критик за все роли |
| Гибрид | да, если есть осмысленная комбинация | по желанию |
| Прототипы | лидер + базовый вариант (+ второй, если позволяет бюджет) | только по просьбе |

Режимы комбинируются: экспресс + команда, полный + автопилот и т.д.

## Как проходит прогон: 15 этапов

| # | Этап | Что происходит | Остановка для вас |
|---|---|---|---|
| 0 | Чтение папки | Читает все файлы, ищет противоречия и пробелы, разбирает существующий код | |
| 1 | Уточнение условий | grill-me только про условия: цель, данные, ограничения, команда, дедлайн, действия во внешнем мире. Веса критериев — через swing-вопросы | ответы на вопросы |
| 2 | Бриф | Цель, ограничения, веса, **абсолютные пороги** для каждого критерия | **подтвердить бриф** |
| 3 | Сценарии | Конкретные тест-кейсы с проверяемыми критериями; 20–30 % откладываются в запечатанный файл | |
| 4 | Волна A | Семейства архитектур и первая половина кандидатов — **до** поиска готовых решений | |
| 5 | Готовые решения | Победители похожих хакатонов, open source, готовые API | |
| 6 | Волна B | Остальные кандидаты с учётом найденного; проверка разнообразия; правило остановки | |
| 7 | Скрининг | Критик отсеивает нарушителей ограничений и доминируемые варианты, оставляет около половины | **вернуть, вычеркнуть или добавить вариант** |
| 8 | Ресерч | Вопросы в порядке ценности информации; останавливается, когда ответы уже не могут сменить лидера | |
| 9 | Панель критиков | Анонимные ярлыки, свой порядок у каждого критика, разные входные данные; оценки считает скрипт | |
| 10 | Гибрид | Комбинация лучших частей против «лидер + дешёвый фикс» (P+), проверка на отложенных сценариях | |
| 11 | Прототипы | Лидер (вокруг самого рискованного допущения) против простейшего варианта | **одобрить объём и стоимость** |
| 12 | Отбор | До 5 вариантов: сильных и разных | |
| 13 | Отчёт | `ARCHITECTURE-REPORT.md` с выжимкой на один экран | |
| 14 | Решение | Вы выбираете вариант → ADR и план сборки | **выбрать вариант** |

### Почему этапы устроены именно так

- **Вопросы только про условия.** Если спрашивать «какую архитектуру хотите», скилл повторит ваши догадки. Его работа — предложить то, до чего вы бы не дошли сами.
- **Две волны генерации.** Если сначала найти похожие проекты, все кандидаты стягиваются к ним. Первая половина придумывается вслепую.
- **Правило остановки вместо квоты.** Когда новые идеи отличаются от старых меньше чем по 3 из 9 осей, генерация останавливается. Пятнадцать вариантов «для галочки» тратят время на всех следующих этапах.
- **Анонимные критики.** Название, порядок и «продающие» формулировки влияют на оценки, поэтому критики видят нейтральные карточки под буквами A, B, C.
- **Абсолютная шкала.** «5» означает, например, «p95 ≤ половины целевой задержки», а не «лучший из вариантов». Добавление нового кандидата не меняет оценки остальных.
- **Арифметика в скрипте.** Модель плохо считает в уме медианы и взвешенные суммы. Все числа в отчёте берутся из `score.py`.
- **Гибрид против P+.** Гибрид строится после чтения критики и подгоняется под найденные минусы. Поэтому он сравнивается с честным конкурентом — «лидер + самый дешёвый фикс» — и проверяется на сценариях, которых не видел.
- **Прототип против базового варианта.** Прототипировать только двух лидеров — значит подтверждать то, что и так впереди. Самая полезная находка — «простой пайплайн проходит почти столько же».

## Как читать результат

Начните с раздела **«One-page summary»** в начале отчёта: там всё решение на одном экране.

**Итоговый балл (Total, %)** = Σ((медиана оценки − 1) / 4 × вес). Все оценки «1» дают 0 %, все «3» — 50 %, все «5» — 100 %.

**Win share (доля побед)** — в каком проценте из 2000 случайных «встряхиваний» весов (каждый вес ×0.7–1.3) и неуверенных оценок вариант оказывается первым.
- ≥ 80 % — лидер устойчив;
- 60–80 % — вероятный лидер;
- **< 60 % — ничья.** Выбор зависит от ваших приоритетов, и отчёт даёт условную рекомендацию.

**Критические веса** — что должно измениться, чтобы сменился лидер. Например: «если задержка для вас важнее примерно вдвое, лидирует C7». Из них строится рекомендация «если важнее X — берите A».

**Метки доказательности** у каждой оценки:

| Метка | Значит |
|---|---|
| **M** (measured) | Измерено на прототипе. Перекрывает всё остальное |
| **R** (researched) | Подтверждено находкой из ресерча |
| **W** (walkthrough) | Следует из прохода по сценарию |
| **A** (assumption) | Общие знания или суждение |

**Уверенность** (high / medium / low) — доля веса, подкреплённая M и R: ≥ 60 % → high, ≥ 30 % → medium.

**Расхождения критиков** (разброс ≥ 2 балла) не усредняются, а выносятся отдельно с аргументами сторон. Часто это самые важные находки.

**Волна A/B** у каждого варианта показывает, придуман он вслепую или под влиянием найденных решений.

## Как следить за процессом

- **Дашборд `progress.html`.** Этапы, блоки «Сейчас» и «Дальше», воронка кандидатов, таблица со статусами, волнами и баллами, вопросы ресерча по убыванию VOI, прототипы, лог. В браузере обновляется сам каждые 4 секунды. В автопилоте показывается бейдж AUTOPILOT, а на контрольной точке — жёлтая плашка «Waiting for you».
- **Список задач в Claude Code.** Этапы с галочками и подпунктами: вопросы ресерча, критика по финалистам, прототипы.
- **Статус в чате.** Три строки на каждой границе этапа.
- **claude.ai.** Файлы там не «живые», поэтому дашборд показывается на контрольных точках и в конце.

Если сессия оборвалась, запустите скилл снова с той же папкой. Он найдёт `progress.json` и предложит продолжить с места остановки.

## Командный режим

N человек, у каждого своя сессия Claude, один git-репозиторий. Этапы, которые можно распараллелить (сценарии, обе волны генерации, поиск решений, ресерч, критика, прототипы, отчёт), делятся на задачи. Последовательные этапы (чтение, вопросы, бриф, скрининг, гибрид, отбор, решение) выполняет сессия лида: она единственный автор общих файлов. Решает не только лид: на чекпоинт отвечает любой участник, а вопрос внутри своей задачи участник решает сам (см. «Важно знать»).

### Как начать

1. **Лид** (его сессия ведёт прогон и пишет общие файлы; на вопросы отвечает вся команда):
   ```
   /architecture-planner --input ./hackathon --team 3
   ```
   Скилл создаст прогон и выдаст команду для остальных.
2. **Участники**: `git pull`, затем в своём Claude Code:
   ```
   /architecture-planner --run hackathon-1005 --member boris
   ```
3. Дальше агенты сами берут задачи. Кто закончил свои, забирает ещё не начатые чужие.

### Безопасность вашей ветки

Состояние прогона хранится в **отдельной ветке `arch/<run>`** без истории проекта. Она подключена как отдельный рабочий каталог (git worktree) в `.arch/<run>/`.

- Скрипт **никогда** не коммитит, не ребейзит, не стешит и не пушит вашу текущую ветку. Ваши непушнутые коммиты остаются локальными.
- `.arch/` скрыт от `git status` через `.git/info/exclude`; ваш `.gitignore` не меняется.
- Пушится только ветка `arch/<run>`.
- Если remote несколько, укажите нужный: `--remote <имя>`. Он запомнится.

### Несколько сессий на одном компьютере

- **Проще всего — git worktree:** `git worktree add ../проект-2`, вторая сессия запускается там. Worktree одного репозитория видят прогон друг друга даже без remote.
- Или отдельный клон (нужен общий remote).
- Или одна общая папка без git: переменная окружения `ARCH_NO_GIT=1` в каждой сессии.
- Один аккаунт GitHub на всех — нормально: участники различаются по `--member`.
- Чтобы держать две подписки Claude на одном компьютере, вторую сессию можно запустить с отдельной папкой конфигурации: `CLAUDE_CONFIG_DIR=~/.claude-second claude`.

### Важно знать

- Участники не видят разговор лида. Бриф пишется подробно: по нему участники решают свои вопросы сами.
- Вопрос внутри своей задачи (метод, источник, библиотека, неясная формулировка) участник решает сам и пишет в файл задачи, раздел `## Decisions`: что выбрал, почему, как откатить. Лиду не пишет.
- Концептуальный вопрос (бриф, веса, отсев вариантов) работу не блокирует. Участник берёт рекомендованный вариант как `assumed`, пишет его в `## For the checkpoint` и идёт дальше. Команда решает его на ближайшем чекпоинте.
- Необратимое (траты сверх бюджета, итоговый выбор, запись вне папки прогона, holdout вне этапов, которым он положен: проверка гибрида, прототипы, отчёт) участник не делает. Его `assumed` — безопасный вариант: не тратить, не открывать, ADR `proposed`. Вопрос идёт на чекпоинт.
- Merge-задача собирает все решения в `TEAM-DECISIONS.md` прогона. Любое решение видно всем. Откат — через чат команды: его записывает сессия лида в merge или новой задачей. Чужой файл задачи не правят — иначе `sync` падает.
- Вопрос чекпоинта сессия лида пишет в `checkpoint-<этап>.md` и сразу делает `team.py sync`. Участники видят его у себя, отвечает любой. Grill — интервью в разговоре лида: отвечает человек лида, команда помогает в чате и подтверждает итог на чекпоинте брифа. Два разных ответа и спор не решён — остаётся ★.
- Ускорение не в N раз: этапы лида последовательные. Для 3 человек реалистично в 1,5–2 раза.
- Командный дашборд: `.arch/<run>/.local/board.html` — задачи каждого этапа цветными плашками и таблица нагрузки по людям.

## Автопилот

Для прогонов без вас: «сделай, пока я сплю», запуск по расписанию.

```
/architecture-planner --input ./hackathon --autopilot yes --budget 5
```

Включить посреди прогона: «я ухожу, решай сам».

**Что происходит:**
- Вопросы grill-me всё равно формулируются, но принимаются рекомендованные ответы. Они попадают в бриф в раздел «Assumptions taken on autopilot — please review».
- На каждой контрольной точке выбирается рекомендованный вариант и записывается в `AUTOPILOT-DECISIONS.md`.
- Отчёт начинается с блока **«Принято без вас»**: какие решения проверить в первую очередь и какие из них сильнее всего влияют на рейтинг.

**Что автопилот никогда не делает сам:**
- не тратит на прототипы больше `--budget`; без бюджета прототипы пропускаются с пометкой «no budget approved»;
- не пишет в репозиторий вне рабочей папки (например, в `docs/adr/`);
- не пушит ничего, кроме ветки `arch/<run>`;
- не принимает финальное решение: ADR пишется со статусом **`proposed`**, а не `accepted`.

## Справочник по скриптам

Скрипты лежат в `scripts/`, используют только стандартную библиотеку Python и выводят JSON. Обычно их вызывает сам агент; вручную они нужны для отладки или если хотите посмотреть состояние.

Во всех командах `progress.py` и `score.py` передавайте `--workdir <рабочая папка>` (иначе берётся `$ARCH_WORKDIR`, затем `./_arch`).

### `progress.py` — прогресс (одиночный режим)

```bash
P="python scripts/progress.py --workdir hackathon/_arch"

$P init --task "Агент для тикетов" --lang ru --mode full [--autopilot yes --budget 5]
$P stage <id> start|done|skip [--note "итог в одну строку"]
$P now "что делаю сейчас"
$P next "шаг 1" "шаг 2"
$P wait "что нужно от пользователя"          # в автопилоте не блокирует
$P cand add C1 "Название" "Идея" [--wave A|B]
$P cand set C1 finalist|screened_out|selected|proposed [--score 0..100] [--reason "..."] [--wave A|B]
$P q add R1 "Вопрос" [--cand C1,C3] [--voi 0.12]
$P q set R1 searching|answered|not_found [--answer "..."] [--confidence high|medium|low] [--voi 0.12]
$P proto add C3
$P proto set C3 running|done|failed [--result "8/10, p50 2.1 s"]
$P artifact path/to/file.md [--label "Подпись"]
$P autopilot yes|no [--budget 5]
$P log "сообщение"                            # "AUTOPILOT: ..." также пишется в AUTOPILOT-DECISIONS.md
$P status                                     # где остановился прогон (для продолжения)
$P todos                                      # список задач для TodoWrite (JSON)
$P render
```

Идентификаторы этапов: `read grill brief scenarios wavea priorart generate screen research critique hybrid prototype select report decide`.

### `score.py` — оценки и вся арифметика

```bash
S="python scripts/score.py --workdir hackathon/_arch"

$S init --defaults --actions yes|no       # критерии, веса и шаблоны порогов по умолчанию
$S init --criteria-file criteria.json     # или свои критерии
$S weights --swing quality=100 latency=60 safety=40 ...   # веса из swing-ответов, сумма 100
$S finalists C1 C3 C6
$S anonymize --lenses reliability,builder,stakeholder [--seed N] [--add H1 P1]
$S add --cand C1 --criterion latency --lens builder --score 4 \
       --evidence researched --justification "anchor 4: p95 1.8 s <= 2 s" [--source "06-research.md R2"]
$S import entries.json                    # оценки одной линзы списком
$S validate                               # код выхода 1 при ошибках
$S aggregate [--no-progress]              # медианы, итоги, расхождения, уверенность; обновляет дашборд
$S table [--format md|json]               # готовые таблицы для отчёта
$S sensitivity [--runs 2000] [--seed 42] [--cands H1,P1]
$S voi --plan research-plan.json [--runs 2000] [--seed 42]
$S diversity --md 03-candidates.md [--min-axes 3]
```

**Критерии по умолчанию** (id → вес без действий во внешнем мире / с действиями):
`quality` 24/23, `reliability` 14/14, `build_speed` 14/14, `cost` 10/9, `latency` 9/9, `debuggability` 9/9, `evaluability` 5/4, `extensibility` 5/4, `demo` 5/4, `safety` 5/10.

**Формат записи оценки:**
```json
{"cand": "B", "criterion": "latency", "lens": "builder", "score": 4,
 "evidence": "researched", "justification": "anchor 4: p95 1.8 s <= 2 s", "source": "06-research.md R2"}
```

**Что проверяет `validate`:** оценки от 1 до 5; допустимые уровни доказательности; веса в сумме 100; у каждой оценки есть обоснование; у каждого критерия с весом заданы пороги всех пяти уровней; нет неизвестных критериев; у каждого финалиста есть оценка по каждому критерию с весом больше 0.

**Формат `research-plan.json`:**
```json
{"questions": [
  {"id": "R1", "text": "Держит ли модель tool calling при 30+ инструментах?",
   "p_yes": "medium",
   "affects": [{"cand": "C1", "criterion": "reliability", "if_yes": 4, "if_no": 2}],
   "status": "open"}
]}
```
`p_yes`: `low` / `medium` / `high` (0.25 / 0.5 / 0.75) или число. VOI — вероятность, что ответ сменит лидера сверх уже существующей неопределённости. Вопрос, который не влияет на лидера, получает ровно 0. Ресерч останавливается, когда у всех оставшихся вопросов VOI < 0.05.

### `team.py` — командный режим

```bash
T="python scripts/team.py"

$T init  --run R --member anna --input ./hackathon --express no --team 3 [--task "название"] [--autopilot yes --budget 5] [--remote origin]
$T join  --run R --member boris
$T stage --run R --member anna <stage> start|done|skip [--note ".."]   # только лид
$T plan  --run R --member anna <stage> --tasks-file plan.json           # только лид
$T next  --run R --member boris [--wait 90]       # по умолчанию 90 с, максимум 540
$T start --run R --member boris <stage> <task>
$T done  --run R --member boris <stage> <task> [--note ".."] [--score N]
$T status --run R
$T todos  --run R --member boris
$T board  --run R
$T sync   --run R --member boris
```

`next` возвращает одно из действий: `task` (сделать задачу), `lead_stage` (этап лида), `wait` (подождать, с полем `retry_after`) или `finished`. Bash-вызов `next` в Claude Code нужно делать с таймаутом не меньше wait + 30 секунд.

Формат плана задач (`plan.json`):
```json
[
  {"id": "R1", "title": "Точность tool calling", "instructions": "Что прочитать, что и в каком формате записать"},
  {"id": "R-merge", "title": "Собрать 06-research.md", "merge": true}
]
```
Обычные задачи раздаются по кругу. Задача с `"merge": true` достаётся лиду и открывается, когда все остальные готовы.

## Windows

- Если `python` не находится, используйте `py`.
- Пути в командах пишите через `/`.
- План задач в командном режиме передавайте файлом (`--tasks-file`), а не JSON в кавычках: PowerShell ломает кавычки.
- Вывод скриптов принудительно в UTF-8, кириллица в консоли не ломается.
- Для командного режима нужен Git for Windows с настроенной авторизацией к remote.

## Частые проблемы

| Проблема | Что делать |
|---|---|
| «No progress.json in …» | Не тот `--workdir` или прогон ещё не начат. Проверьте путь |
| «Run … already exists» при `team.py init` | Такой прогон уже есть: присоединяйтесь через `join` или выберите другой `--run` |
| «Branch arch/… not found» при `join` | Лид ещё не запустил `init` или не смог запушить. Попросите лида выполнить `team.py sync` |
| «Several remotes …; pass --remote NAME» | Добавьте `--remote <имя>` к `init` или `join`; он запомнится |
| `sync: error` | Повторите `team.py sync`; если не проходит — проверьте доступ к remote (`git fetch`) |
| `next` обрывается | Таймаут Bash меньше времени ожидания: используйте `--wait 90` и таймаут ≥ 120 с |
| `validate` ругается на `<target>` | В порогах остались заготовки: впишите реальные значения из брифа в `scores.json` |
| «hole: finalist … has no score» | Какой-то критик не оценил финалиста по критерию; дооцените и повторите `aggregate` |
| Прогон старой версии в командном режиме не подхватывается | Начните новый прогон; подробности в `CHANGELOG.md` |

## Ограничения

- **Это не измеренный сеньор.** Скрипты проверены тестами, но качество суждений модели проверяется только живыми прогонами. Лучшая проверка — прогнать скилл по условиям ваших прошлых проектов и сравнить с тем, что реально произошло.
- **Критики — одна модель в разных ролях.** Анонимизация, перемешивание и разные входные данные снижают корреляцию ошибок, но не убирают её. Если можно выбрать другую модель для одной из ролей, скилл это сделает. Отчёт честно пишет, насколько независимой была панель.
- **Без субагентов** изоляция отложенных сценариев и волны A держится на инструкциях; отчёт помечает это как «weaker holdout».
- **Скорость сборки прототипа Claude ≠ скорость вашей команды.** Она остаётся оценкой с поправкой на навыки из брифа.
- **Полный режим долгий и тратит токены**, а прототипы — ещё и API-бюджет. При жёстком дедлайне берите экспресс.
